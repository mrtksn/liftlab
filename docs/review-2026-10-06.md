# Review — 2026-10-06

Reviewed source at `d5911e3`, focusing on hardware wiring/install, AI tools, native control behavior and deployment documentation. Application code and firmware were left unchanged. This is a source/host-test review; no physical boards, sensors or flight were exercised.

## Findings

### 1. P1 — Pi flight/latch control accepts unauthenticated network commands

`runner/pi/dfb_pi.c:272–274` binds its UDP listener to `INADDR_ANY`; `293–313` accepts commands from any sender and dispatches them to the pilot, learning and cargo handlers. Default port: 14560. Generated installation services retain this default. A host that can reach the listener can send commands including disarm or latch release. There is no sender check or authentication.

`--port 0` still creates and binds the socket, selecting an ephemeral port. It is not a disable switch. This differs from the native ground controller, which defaults to loopback and treats port 0 as disabled.

Pending fix: default to loopback, support disabling the socket, require explicit LAN opt-in and define authentication for remote actuation. Temporary mitigation: firewall/network isolation restricting access to the Pi listener. Regression checks: default bind address, disabled listener, rejected untrusted commands, and explicitly enabled authorized remote commands. Source-confirmed; no commands were sent to hardware.

### 2. P2 — Airframe upload bypasses wiring/custom-firmware checks

`js/install-ui.js:329–333` uploads an airframe without consulting `boardWiringPlan`, custom-firmware acknowledgement, or applied settings/reboot state. The separate hardware-settings action at `335–350` checks wiring and custom-driver requirements. The airframe button remains independent of it.

A stubbed invocation of the actual upload function with a GPIO conflict, a custom sensor and `INST.customFirmware=false` sent an AIRFRAME frame, called the wiring planner zero times, and reported success. The native output checks only confirm there are enough configured outputs; they do not prove that the design's GPIO/driver settings are installed. For example, a brushed-MOSFET design can be sent while the board still uses default ESC pulses.

Pending fix: validate the hardware plan on every physical upload, gate unsupported/custom configurations, and track matching settings plus completed restart before enabling airframe transfer. Regression checks: conflicts block writes; custom firmware requirements apply to both actions; changed motor drivers require settings/reboot; a confirmed valid sequence permits transfer. Until then, follow wiring → save/reboot → `show` verification → airframe, with MOSFET power disconnected while configuring.

### 3. P2 — AI board read/edit round trip fails

`js/agent-tools.js:118–120` includes read-only `flight_loop_hz` in the flight-core board returned by `get_computers`. `js/agent-hardware.js:35` rejects fields other than `id`, `name`, `kind` and `tasks` in `set_computers`.

Reproduced using the registered tools in a Node VM: read `get_computers().boards`, then pass that array to `set_computers({boards})`. It throws `board: unknown field flight_loop_hz`. A straightforward read/rename/write operation can therefore fail despite preserving board IDs.

Pending fix: separate read-only metadata from editable boards, or explicitly tolerate/strip it while retaining validation of editable fields. Regression check: get → rename/reorder → set preserves IDs/wiring and succeeds. Temporary workaround: send only the four editable fields.

### 4. P2 — Native navigation suite fails locally and is absent from CI

`runner/fc/test_nav.c:174` fails its GPS position-hold limit: maximum error 0.803399 m against a strict 0.8 m limit. The landing test at `195–197` also fails: horizontal drift is 1.02 m against a 0.8 m limit. Both reproduced on two unmodified executions on macOS arm64, compiled with the same flags as `runner/test.sh`. A temporary diagnostic copy changed only the printed precision to obtain the hold error.

Reproduce from the repository root without rewriting WebAssembly artifacts:

```sh
cc -O2 -Wall -Wextra -Irunner -o /tmp/liftlab-test-nav \
  runner/fc/test_nav.c runner/fc/nav_core.c runner/fc/fc_core.c \
  runner/rn_host.c runner/rn.c runner/rn_builtin.c -lm
/tmp/liftlab-test-nav runner/fc/testdata
```

The cause is not established. The test uses C `rand()` with `srand(7)`, so the same seed does not establish identical noise samples across host libraries. The near-boundary hold failure and the larger landing error need investigation before changing tolerances or claiming a real-flight defect.

`.github/workflows/boards.yml` builds firmware/host programs and runs wiring/driver tests, but omits the native flight, navigation, runner-host, link, cargo, telemetry and ground behavioral suites. A passing workflow can therefore coexist with these failures. Pending work: investigate both failures, use reproducible test noise across platforms, and run portable behavioral suites in host CI. Keep Linux-only Pi end-to-end tests separate from macOS-compatible tests.

### 5. P2 — AI install readiness misses unsupported MCU navigation

`js/agent-hardware.js:134–140` derives readiness from wiring errors and the presence of the MCU flight core, without checking task support. Reproduced with an S3 board running `core`, `tlm` and `nav`: `get_install_settings` returns `ready:true` with no warnings even though native MCU navigation is not integrated. The Install UI does display that limitation (`js/install-ui.js:172`).

Pending fix: share physical role/device capability checks between the UI and agent; distinguish “valid wiring settings” from “all assigned tasks deployable.” Regression checks: MCU navigation/cargo and unsupported distributed devices report explicit blockers or warnings, while supported ESP/Pi roles remain available.

### 6. P3 — Custom IMU diagnostic falsely reports no gyro

`runner/fc/esp32/main/hw.c:88` records a successful custom IMU as kind 3. The custom read path accepts its gyro samples (`164`), and startup gyro calibration supports it. However, the legacy telemetry gyro flag at `runner/fc/esp32/main/flight.c:245` is set only for kind 1. The install status at `js/install-ui.js:306` renders the missing flag as **NO GYRO**.

Pending fix: derive this diagnostic from gyro capability/sample state, including custom drivers, rather than the built-in driver ID alone. Regression checks: built-in gyro and custom gyro report correctly; accelerometer-only and absent/failed sensors remain distinguishable. Source-confirmed; not reproduced on a physical module.

## Remaining capability gaps

- Custom sensor C is saved/exported; browser compilation, register emulation and automatic source/binary matching are not implemented. Native drivers are trusted C and need chip-specific rebuilds.
- Physical outputs/I²C sensors reside on the flight-core ESP. Pi I²C, MCU navigation/cargo, distributed motors/servos, optical-flow hardware and Pi load-switch inputs are missing. See the [board capability table](boards.md).
- Brushed output supports active-high, one-direction duty PWM. H-bridge, DShot and custom motor protocols are absent. Simulation still uses the generic brushless response model. Duty ceilings clip after allocation, while headroom and native learning telemetry use the full model/requested throttle.
- Board CI compiles six firmware combinations but does not replace the checked-in downloadable binaries or manifest. Pages publishes static committed files. Native source, browser WebAssembly and served firmware need separate artifact validation; see [deployment](deployment.md).
- Real sensor compatibility, GPIO waveforms, loop timing and flight behavior remain unverified for the new board/driver combinations. Existing ESP32 runner bench measurements do not establish this broader hardware coverage.
